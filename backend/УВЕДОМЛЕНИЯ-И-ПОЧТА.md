# Уведомления и подтверждение почты · 1.6.4 / 0.2.4

## Что уже сделано

Проект Supabase Free создан владельцем, базовая схема друзей и бета-доступа выполнена. Публичная конфигурация уже включена в клиент. В этом обновлении добавлен колокольчик «Уведомления»: только входящие ожидающие заявки, онлайн-ник отправителя, его опубликованная аватарка и решения «Принять» / «Отклонить». Заявки хранятся в существующей friendships — отдельные дубли не создаются. Счётчик означает ожидающие решения заявки, а не число просмотров. Исходящие и принятые не считаются.

Обновление при открытии, возвращении в окно, действиях и каждые 30 секунд в видимом окне. При закрытом лаунчере push-уведомлений нет. Локальный профиль и вишлист работают без почты; для друзей нужен отдельно подтверждённый онлайн-профиль.

## 1. Обновить уже существующий сервер

В Supabase → SQL Editor → новый запрос вставить **весь** `friend-notifications.sql` (тот же файл выдан отдельно как `Temka-Launcher-Notifications-Update.sql`) и Run от роли postgres.

Ожидаемый результат: `TEMKA_NOTIFICATIONS_READY`.

Скрипт можно повторять: данные не удаляет. Добавляет ограничительную RLS-политику к существующим правилам; проверяет email_confirmed_at в Auth, защищает поиск и список друзей. Ограничение действует на сервере, а не только в кнопках клиента. Анонимного доступа к таблицам не добавляет. Новая таблица уведомлений не требуется.

**Из чата обновление в рабочую БД не выполнялось.** Оно необходимо для полной серверной защиты. Не пересоздавай проект и не удаляй таблицы ради обновления.

Для совершенно нового проекта: сначала исходный `supabase.sql` один раз, затем `beta-access.sql`, затем `friend-notifications.sql`. Для текущего проекта первые два уже выполнены владельцем.

## 2. Включить настоящие письма

В Authentication → Email / Emails проверь, что Email и подтверждение email включены. Затем настрой Custom SMTP с разрешённым отправителем. Стандартный тестовый отправитель Supabase не подходит для обычной регистрации всех друзей: получатели и частота ограничены.

SMTP-пароль / пароль приложения вводится **только в настройках Supabase**, не в лаунчер, исходники, ZIP, GitHub и не в чат. Отправитель должен принадлежать тебе или быть разрешён твоим почтовым провайдером. Не выключай подтверждение email ради обхода ошибки доставки.

Открой шаблоны **Confirm signup** и **Magic Link**. Для обоих можно использовать `Temka-Email-OTP.html`, тема: `Код подтверждения TemkaLauncher`. Вставлять именно HTML-код шаблона с неизменённым `{{ .Token }}`, не изображение предпросмотра. Это одноразовый код, который вводится в лаунчере; ссылки подтверждения не требуются этому интерфейсу. Для нового пользователя используется подтверждение регистрации, для повторного входа — код входа.

Почтовый провайдер пока не выбран/не настроен из чата. Ни одно реальное письмо и ни один реальный аккаунт тестами этого обновления не создавались.

## 3. Выпустить клиент и проверить вдвоём

- ПК: новый ZIP → Publisher 1.0.9 → вкладка лаунчера → новый свободный номер, не перезапись существующего тега.
- Мобильный ZIP — полный Android/iOS проект с обновлёнными web-assets; нужен отдельный native build. Это не APK/IPA.
- Пользователь A: Профиль → получить код на **свою** почту → ввести код → сохранить онлайн-ник (3–25 символов).
- Пользователь B: та же процедура с **другой** почтой и другим онлайн-ником.
- A ищет полный онлайн-ник B и отправляет заявку. У B появляется счётчик; в «Уведомлениях» видно A. Принятие добавляет обоих в друзья; отклонение удаляет ожидающую заявку. Проверь повторный вход/обновление списка на обоих устройствах.
- Без подтверждения почты клиент предлагает подтверждение вместо друзей; сервер также должен отклонять действия. Неверный код не даёт доступа.
- Только после настоящего входа владелец берёт собственный проверенный UUID в Auth → Users для назначения creator_admin по инструкции бета-доступа. Локальный ник не даёт этой роли.

## Границы проверки

Unit и браузерные тесты используют имитацию Auth/HTTP — это не проверка SMTP. SQL проверен на одноразовой локальной PostgreSQL-базе с имитацией Auth и ролей. Production Supabase, два настоящих аккаунта, почта, обновление через GitHub, Windows/native Android/iOS ещё требуют реальной проверки владельцем. Новые Windows EXE, APK и IPA не создавались.
