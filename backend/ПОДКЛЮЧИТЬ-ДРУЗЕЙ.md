# Настоящие друзья и коды на почту

Код готов, но **живой проект Supabase и отправка писем ещё не настроены**. Без них лаунчер честно показывает «Сервер друзей ещё не подключён» и не выдумывает пользователей. Ввод обычного локального ника не создаёт аккаунт в общей базе.

## Что добавлено

- Отдельный онлайн-профиль: вход/создание по одноразовому коду на почту.
- Онлайн-юзернейм 3–25 символов, уникальный без учёта регистра.
- Поиск по **полному** юзернейму, например `temka_play_official`, без выдачи чужой почты.
- Заявки в друзья, принятие, отклонение, отмена, удаление из друзей.
- Публикация аватарки для других игроков отдельной кнопкой. Локальная картинка сама на сервер не отправляется.
- Значок «Создатель · Администратор», назначаемый только владельцем базы по подтверждённому ID аккаунта, не по набранному нику.

Старые локальные профили не удаляются и не становятся облачными автоматически. Их пароли и почты не загружаются в базу. Локальный ник и онлайн-юзернейм могут различаться. Удаление локального профиля в лаунчере не удаляет онлайн-аккаунт. Онлайн-аккаунт и его связанные строки владелец пока может удалить в Supabase Auth → Users; опубликованные изображения отдельно удаляются в Storage. Самостоятельное удаление онлайн-аккаунта из интерфейса — последующее расширение.

## Подключение владельцем

1. Создай **новый отдельный проект Supabase** под своим аккаунтом. Сохрани пароль базы у себя; в чат его не присылай.
2. В **SQL Editor** выполни файл `backend/supabase.sql`. Он предназначен для однократного запуска в новом проекте. Если повторный запуск сообщает, что policy уже существует, не удаляй рабочие таблицы с пользователями — сначала проверь, что миграция уже применена.
3. В **Authentication** включи вход через Email и разреши новые регистрации.
4. Настрой **SMTP** с реальным отправителем, которому разрешено отправлять письма. Тестовая отправка сервиса может иметь ограничения; для обычных пользователей нужна подходящая почтовая конфигурация. SMTP-пароль вводится только в настройках провайдера, **никогда не в код сайта или лаунчера**.
5. В шаблонах писем **Magic Link** и **Confirm signup** включи одноразовый код:

   ```html
   <h2>Вход в TemkaLauncher</h2>
   <p>Твой код: <strong>{{ .Token }}</strong></p>
   <p>Если ты не запрашивал вход, просто проигнорируй письмо.</p>
   ```

   Это именно код для ввода в лаунчере, а не только ссылка. Срок действия и ограничения повторной отправки настраиваются на стороне Auth. Клиент поддерживает цифровые коды длиной 6–10 символов и повторную отправку не чаще раза в минуту через интерфейс; серверные лимиты остаются обязательными.
6. В настройках проекта возьми **Project URL** вида `https://…supabase.co` и **publishable key** либо старый **anon public key**. Это клиентская публичная конфигурация. **Не используй service_role и ключи `sb_secret_…`**. Сборка отклоняет такие ключи до создания интерфейса.
7. В GitHub-репозитории **лаунчера**, не сайта, открой **Settings → Secrets and variables → Actions → Variables** и создай:

   - `TEMKA_SUPABASE_URL` — Project URL;
   - `TEMKA_SUPABASE_ANON_KEY` — publishable/anon ключ.

8. Выпусти новую версию через **Publisher 1.0.5**. Workflow передаст публичные настройки в Windows- и Linux-сборки. Обычным игрокам вводить настройки не нужно.

Если настройки добавлены после выпуска 1.5.3, нужен **новый номер версии**, например следующий предложенный Publisher. Не перезаписывай опубликованные релизы: установленные лаунчеры определяют обновления по версии.

Для локальной сборки переменные называются `VITE_TEMKA_SUPABASE_URL` и `VITE_TEMKA_SUPABASE_ANON_KEY`. Их можно задать в `.env.local`, который игнорируется Git и Publisher. Пример имён — в `.env.example`.

## Сделать твой аккаунт создателем

1. После настройки войди в лаунчере в онлайн-профиль через код **на свою почту**.
2. В Supabase открой **Authentication → Users**, найди именно свою подтверждённую почту и скопируй **User UID**.
3. В привилегированном SQL Editor выполни, заменив пример своим настоящим UID:

   ```sql
   insert into public.creator_roles(user_id, role)
   values ('ТВОЙ_ПОДТВЕРЖДЁННЫЙ_USER_UID', 'creator_admin');
   ```

4. Вернись в лаунчер, обнови профиль и сохрани юзернейм **temka_play_official**.

Обычный пользователь не может назначить себе эту роль через API. Ники `temka_play_official` и `temka_play` зарезервированы для серверной роли создателя. Простая запись такого имени в локальном профиле никаких онлайн-прав не даёт. Значок появится в онлайн-профиле и поиске. Полноценная панель модерации пока не реализована.

## Проверка перед приглашением игроков

- Создай два тестовых онлайн-аккаунта на разных почтах/устройствах.
- Проверь реальную доставку первого и повторного кода, неверный/просроченный код, выход и повторный вход.
- Сохрани разные юзернеймы. Найди второго игрока, отправь заявку, прими её с другой стороны.
- Проверь, что третье лицо не видит заявки и не может их менять.
- Загрузи свою картинку локально, затем осознанно нажми «Опубликовать аватарку для друзей».
- Проверь удаление изображения, а также обновление списка после смены ника.

Изображения в bucket `avatars` публичные. Они могут кешироваться у клиентов и хостинга; удаление с сервера не гарантирует мгновенного удаления всех копий из кешей. Онлайн-сессия хранится на текущем устройстве отдельно для каждого локального профиля; не используй её на чужом компьютере без выхода. Роли и дружба защищены серверными RLS-политиками, а не клиентским JavaScript. Почта остаётся в Supabase Auth, а не в публичной таблице профилей.

Включи подходящие лимиты Auth, мониторинг и защиту от злоупотреблений до широкого публичного запуска. Если понадобятся CAPTCHA или модерация/блокировки, их нужно отдельно добавить в клиент и backend — сейчас интерфейса CAPTCHA и жалоб нет. Следи за квотами и тарифом провайдера.

## Общий вход в игры — следующий этап

**Вход в Godot-игру через TemkaLauncher здесь ещё не реализован**, исходники игры в этой задаче не изменялись. Следующий этап:

- один подтверждённый `auth.users.id` как идентификатор игрока;
- игровой сервер проверяет подпись, issuer, audience и срок JWT либо обменивает одноразовый короткоживущий билет на игровую сессию;
- Godot-клиент получает только билет/игровую сессию, не SMTP-пароль, не service_role и не пароль пользователя;
- билеты одноразовые, привязанные к игре, с коротким TTL; передача refresh token в URL/аргументах запуска запрещена;
- аккаунт, ник и права подтверждает сервер, а не присланная клиентом строка `temka_play_official`.

Сначала нужно поднять и проверить реальную почту и общую базу; затем связывать её с конкретным игровым сервером. Нынешний сайт остаётся без аккаунтов.
