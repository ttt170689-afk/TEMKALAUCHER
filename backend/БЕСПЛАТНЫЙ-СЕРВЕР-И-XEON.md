# Как включить друзей: бесплатно, в облаке или на Xeon

Коротко: **для первых тестов с другом рекомендую Supabase Cloud Free**. Домашний Xeon имеет смысл, если хотите сами обслуживать Linux, интернет-доступ и резервные копии. Ничего из этого здесь ещё не развёрнуто.

## Почему друзья сейчас не появляются

Локальные профили хранятся на каждом компьютере отдельно. Чтобы два лаунчера увидели друг друга, им нужны:

1. **Один общий сервер/проект**, не по серверу на каждого игрока.
2. Онлайн-авторизация двух разных пользователей.
3. Сохранённые онлайн-профили с разными юзернеймами.
4. Поиск точного онлайн-юзернейма → заявка → принятие.

Одинаковые локальные ники ничего не связывают. Локальная подпись «Разработчик» не выдаёт онлайн-права. Сервер друзей — это база аккаунтов/профилей/заявок, **не сервер мультиплеера TemkaWorld/Fantazia**. Мультиплеер и вход в игры через лаунчер — отдельная будущая интеграция.

## Вариант 1 — бесплатное облако Supabase

На дату проверки 11.10.2026 официальный Free: **$0/месяц**, 500 МБ базы, 50 000 активных пользователей в месяц, 1 ГБ файлов, 5 ГБ исходящего + 5 ГБ кешированного трафика; максимум два активных проекта. Проект приостанавливается после недели неактивности, автоматические бэкапы не включены. 50 000 MAU — лимит месячной аудитории, не обещание 50 000 одновременных подключений. [1](https://supabase.com/pricing)

Для первого прототипа это разумная отправная точка, но расход зависит от профилей, аватарок и запросов. Перед использованием проверь текущие условия тарифа в кабинете. Не включай платный план или дополнительные услуги, если хочешь остаться в бесплатном лимите.

### Порядок действий

1. Создай **один новый проект** в Supabase, сохрани пароль базы у себя, не в чате.
2. В SQL Editor выполни `supabase.sql` из этого комплекта. Это схема для нового проекта. Для существующей базы сначала сделай резервную копию и продуманную миграцию — не запускай случайные сбросы таблиц.
3. Настрой Email Auth и отправку почтовых кодов; в нужных шаблонах нужен `{{ .Token }}`. Подробности — в соседней инструкции `ПОДКЛЮЧИТЬ-ДРУЗЕЙ.md`.
4. Текущий клиент друзей использует email-коды. Для произвольных пользователей нужна настроенная доставка писем; бесплатность базы **не гарантирует бесплатный SMTP, домен и любую доставку**. Тестовая почта поставщика имеет ограничения — обязательно проверь отправку на два реальных адреса. Если SMTP пока нет, серверная часть ещё не готова к нормальной регистрации игроков.
5. В репозитории `ttt170689-afk/TEMKALAUCHER`: Settings → Secrets and variables → Actions → **Variables**:
   - `TEMKA_SUPABASE_URL` = Project URL вида `https://…supabase.co`;
   - `TEMKA_SUPABASE_ANON_KEY` = публичный anon / publishable key.
6. Выпусти новую свободную версию через **Publisher 1.0.7**. Его workflow передаст эти значения во время сборки как `VITE_TEMKA_SUPABASE_URL` и `VITE_TEMKA_SUPABASE_ANON_KEY`. Добавление Variables **не изменяет уже установленные программы**: требуется новая сборка.
7. Установите с другом сборки с одинаковой конфигурацией. Профиль → блок онлайн-друзей → вход каждый на свою почту → подтверждение кода → создание/сохранение онлайн-юзернейма. Локальное имя и онлайн-юзернейм могут отличаться.
8. Первый ищет **точный онлайн-юзернейм** второго и отправляет заявку. Второй обновляет список входящих и принимает. После принятия оба обновляют список друзей.
9. Перезапустите оба лаунчера и убедитесь, что дружба осталась. На двух аккаунтах проверьте также удаление/отклонение заявки. Если письмо не приходит — проверяйте SMTP, лимиты Auth и спам, а не повторяйте запросы бесконечно.

**Никогда не вставляй в сайт, ZIP, программу или GitHub Variables клиента:** `service_role`, `sb_secret`, пароль Postgres, SMTP-пароль. Публичный ключ разрешён только вместе с действующими RLS-политиками. Не отключай RLS ради того, чтобы «быстрее заработало».

Если хочется онлайн-друзей вообще без почты — можно отдельно проектировать вход по логину/паролю и восстановление доступа. Это **не реализовано** в этой версии. Удаление email из вишлиста не меняет схему онлайн-авторизации.

## Вариант 2 — домашний Xeon с другом

Можно, но точный ответ зависит от модели Xeon, RAM, SSD и подключения к интернету. Для полного Docker-стека Supabase официально указаны минимум **2 ядра, 4 ГБ RAM, 40 ГБ SSD**, рекомендуется **4+ ядра, 8+ ГБ RAM, 80+ ГБ SSD**. Это требования стека, не гарантия количества игроков; дополнительные компоненты увеличивают расход. [1](https://supabase.com/docs/guides/self-hosting/docker)

### Что понадобится помимо процессора

- Поддерживаемый Linux, Docker Compose и умение обновлять контейнеры.
- Постоянно включённый компьютер и надёжный интернет. После отключения домашнего сервера друзья/авторизация будут недоступны.
- Доступный снаружи HTTPS-адрес, сертификат, reverse proxy. Для публичного сервиса нужно выяснить ситуацию с белым IP/CGNAT у провайдера; проброс порта сам по себе CGNAT не устраняет.
- Для закрытых опытов вдвоём можно использовать приватную VPN-сеть, не выставляя базу наружу. Публичные игроки без этой VPN её не увидят; HTTPS и клиентская конфигурация всё равно требуют настройки.
- Свои секреты вместо значений из примера, SMTP для текущего email-входа, обновления безопасности, ограничение частоты запросов, мониторинг диска.
- Резервная копия базы **на другой носитель/машину** и проверенное восстановление. RAID сам по себе не является бэкапом.
- Не публиковать Postgres (5432), панель администратора и SSH с простыми паролями. В интернет отдавать только необходимые HTTPS API; администрирование — через защищённый доступ.

**Софт без платы за лицензию ≠ сервер без расходов:** электричество, износ SSD, интернет, возможный домен и ваше время. Оценка энергии: средняя мощность из розетки в ваттах × 24 × 30 / 1000 = кВт⋅ч за месяц. Стоимость умножается на ваш тариф; измерять надо весь сервер, не только TDP CPU.

### Важное ограничение именно этой сборки

`src/lib/online.ts` сейчас принимает только облачный HTTPS-домен `*.supabase.co`. Поэтому **подставить IP Xeon или свой домен и сразу получить рабочие друзья нельзя**.

Для домашнего варианта ещё нужно развернуть совместимый Supabase-стек, настроить URL/Auth/SMTP/TLS, отдельно добавить проверяемую поддержку своего HTTPS-хоста в клиенте, пересобрать лаунчер и протестировать RLS двумя пользователями. В этом комплекте такая доработка и развёртывание **не выполнены**. Удалять проверку адреса без разбора или размещать секретный ключ в клиенте не нужно.

PocketBase или собственный небольшой API могут быть легче полного Supabase, но это другой backend: существующий клиент и SQL нельзя просто подключить к ним сменой URL. Потребуется адаптация авторизации, профилей, заявок и прав доступа.

## Что выбрать сейчас

| Вариант | Лучше для | Что остаётся сделать |
|---|---|---|
| Supabase Cloud Free | Первые тесты с другом, минимальное администрирование | Проект, SQL, доставка email, публичная конфигурация и новая сборка |
| Домашний Xeon | Обучение серверной части и самостоятельный контроль | Всё перечисленное + Linux/сеть/TLS/бэкапы + доработка self-host URL клиента |
| VPS | Работа независимо от домашнего ПК | Найти подходящий тариф, администрировать; постоянную бесплатность не обещаем |

**Мой совет:** сначала свяжите два аккаунта через Free Cloud. Когда это работает и понятна нагрузка, решайте, нужен ли перенос на Xeon. Сайт можно разместить отдельно на GitHub Pages или Vercel — статический хостинг сайта не заменяет backend друзей.
