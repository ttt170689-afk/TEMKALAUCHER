# TemkaLauncher 1.5.2 — публикация через Publisher 1.0.3

Для отправки этого ZIP установи **TemkaPublisher-Setup-1.0.3.exe** и запускай Publisher с нового ярлыка. Закрой старые версии из папки «Загрузки».

1. Выбери ZIP исходников, проверь предложенную новую версию и нажми публикацию.
2. Publisher сам отправляет коммит/тег, затем явно вызывает **workflow_dispatch** с уникальной меткой запроса.
3. Наблюдай за конкретным Run ID. «Ошибка», «Отменено», «Тайм-аут» — итоговые состояния, индикатор останавливается. Успех требует опубликованных EXE/latest.yml/blockmap.
4. Можно отправить запрос отмены кнопкой «Отменить сборку на GitHub». «Не ждать» только выключает наблюдение, не отменяя удалённую работу.

В новом шаблоне **push сам по себе не запускает workflow**. Для ручного выпуска: Actions → Windows EXE and Release → Run workflow → `publish = true`; можно выбрать нужный тег. Pull Request запускает проверки, но не релиз.

В workspace больше нет большого готового установщика лаунчера — он удалён по просьбе пользователя. Исходники сохранены. Готовый EXE должен собрать GitHub после успешной публикации.

Исправления 25-символьного ника и доступных имён компактного меню сохранены. Smoke-тест не отключён. При его ошибке скачай `electron-smoke-diagnostics` из Artifacts.

Новая публикация и реальная отмена из этой сессии не выполнялись; публичный статус предыдущего запуска только прочитан.

# TemkaLauncher 1.5.1 — Windows EXE + автообновление

Подготовлено для **https://github.com/ttt170689-afk/TEMKALAUCHER**.

## Что уже сделано

- Собран установщик `TemkaLauncher-Setup-1.5.1-x64.exe` для **Windows 10/11 x64**.
- Сохранён интерфейс из присланного проекта.

- После загрузки установка начинается по кнопке **«Перезапустить»** или при полном выходе через меню трея. Крестик обычно лишь сворачивает приложение в трей.

- Исправлены несовпадающие версии, отсутствующие зависимости, обработка сетевых ошибок и передача команды проверки из трея в интерфейс.

> **Важно:** файлы подготовлены локально. Из этой сессии изменения НЕ отправлены в GitHub и релиз НЕ опубликован: нет доступа на запись. Для включения доставки обновлений выполни раздел 2.

## 1. Установить и открыть

1. Скачай отдельный файл `TemkaLauncher-Setup-1.5.1-x64.exe`, приложенный к результату работы.
2. Запусти его в Windows и выбери папку установки в пределах своей учётной записи. Установка на компьютер для всех пользователей не используется.
3. Открой TemkaLauncher с рабочего стола или из меню «Пуск».
4. Создай локальный профиль в интерфейсе. Это сохранённая из исходного проекта локальная регистрация, **не сетевой аккаунт**. Не используй для неё пароль от важных сервисов.

Пока в GitHub нет релиза с `latest.yml`, проверка обновлений может завершаться ошибкой. Это не мешает открыть лаунчер. Старые `updates/manifest.json` и ZIP интерфейса больше не используются.

**Цифровой подписи нет.** SmartScreen/антивирус может предупредить о неизвестном издателе. Не отключай защиту Windows; перед запуском проверь источник файла и SHA-256 в `SHA256SUMS.txt`, приложенном к EXE. Для публичного распространения нужен сертификат подписи или соответствующий сервис подписи.

## 2. Отправить проект в твой GitHub и выпустить первую версию

### Через отдельную программу TemkaPublisher.exe

Теперь можно открыть **TemkaPublisher.exe**, войти в GitHub, выбрать этот ZIP, указать новую версию и нажать «Распаковать и опубликовать». Программа сама подготовит файлы, сделает коммит и push тега; GitHub соберёт EXE и опубликует обновление. Git и GitHub CLI устанавливаются отдельной кнопкой. Подробности в инструкции к программе.

При импорте старого ZIP программа сохраняет интерфейс и добавляет актуальную сборочную часть и автообновление. ZIP с одним dist или готовым EXE не подходит: нужны исходники с `package.json`, `src/App.tsx`, `src/lib/auth.tsx`.


### Самый простой путь: готовый скрипт

1. Распакуй `TemkaLauncher-repository.zip` в обычную папку. Не запускай BAT прямо внутри архива.
2. Установи **Git** и **GitHub CLI**. Можно через PowerShell:

   ```powershell
   winget install --id Git.Git -e --source winget
   winget install --id GitHub.cli -e --source winget
   ```

   Либо скачай установщики с https://git-scm.com/download/win и https://cli.github.com/.
3. Закрой и открой терминал после установки программ.
4. Запусти **`PUBLISH-GITHUB.bat`** из распакованной папки.
5. Авторизуйся в браузере через GitHub CLI под аккаунтом с правом записи в `ttt170689-afk/TEMKALAUCHER`. CLI может дополнительно запросить разрешение `workflow`, нужное для записи GitHub Actions. Пароли и токены в чат не отправляй.
6. Проверь имя аккаунта и репозитория. Напиши **`PUBLISH`**, чтобы подтвердить отправку.
7. Открой https://github.com/ttt170689-afk/TEMKALAUCHER/actions. Дождись успешного задания **Windows EXE and Release** с ручным запуском и публикацией.
8. Установщик появится на https://github.com/ttt170689-afk/TEMKALAUCHER/releases/latest.

Скрипт клонирует текущую ветку репозитория во временную папку, накладывает исправленный проект, удаляет несовместимый старый ZIP-апдейтер и делает обычный коммит/push. **Force push не используется**, история сохраняется; посторонние файлы не очищаются. Клон остаётся по пути, который скрипт напечатает. Локальная папка с ZIP не становится клоном удалённого репозитория.

В GitHub Actions должны быть разрешены workflow. Защищённая ветка может запретить прямой push: в этом случае отправляй изменения отдельной веткой и Pull Request. Скрипт не обходит правила доступа. При сетевом сбое после успешного push открой Actions и запусти `windows.yml` вручную с `publish = true`.

Обычный push создаёт сборку в **Artifacts**, но не публичный релиз. Для релиза нужен ручной запуск с `publish = true` либо push тега `v1.5.1`. Скрипт выполняет ручной запуск сам. Готовый релиз не перезаписывается: повторная публикация той же версии завершится ошибкой намеренно.

## 3. Выпуск следующего обновления

В актуальном клоне репозитория после изменения исходников:

```powershell
npm version patch --no-git-tag-version
npm ci
npm test
npm run build
git add .
git commit -m "Release next launcher version"
git push
```

Затем **Actions → Windows EXE and Release → Run workflow → publish = true**. Например, после 1.5.1 получится 1.5.2. Номер версии берётся только из `package.json`; `npm version` обновляет также lock-файл.

Альтернатива — создать и отправить соответствующий тег, например `git tag v1.5.2`, затем `git push origin v1.5.2`. Тег должен совпадать с версией в `package.json`.

Workflow:

1. Проверяет TypeScript и тесты механизма обновления.
2. Запускает smoke-тест Electron: окно, регистрация, настройки, IPC, сохранение сессии.
3. Собирает Windows NSIS EXE и проверяет метаданные и SHA-512.
4. Загружает EXE, `.exe.blockmap` и `latest.yml` сначала в draft-релиз.
5. Публикует релиз целиком. Только после этого его видят установленные лаунчеры.

Репозиторий и релизы должны оставаться **публичными**: секрет GitHub не встроен в клиент. Не удаляй `latest.yml` и `.blockmap`, не меняй содержимое уже опубликованной версии. Не переименовывай репозиторий без миграции адреса обновлений в старых клиентах.

## 4. Сборка EXE у себя

Нужны Windows 10/11 x64 и **Node.js 22 LTS** (не ниже 22.12.0).

Запусти **`BUILD-EXE.bat`**. Или:

```powershell
npm ci
npm test
npm run dist
npm run verify-release
```

Результат находится в `release/`:

- `TemkaLauncher-Setup-1.5.1-x64.exe` — установщик;
- `TemkaLauncher-Setup-1.5.1-x64.exe.blockmap` — карта дифференциального обновления;
- `latest.yml` — версия, размер и SHA-512 установщика.

Это **установочный EXE**, не portable. Он содержит необходимые файлы Electron; конечному пользователю не нужен Node.js. Portable намеренно не выпускается: самообновление NSIS рассчитано на установленное приложение.

### Разработка и проверки

```powershell
npm ci
npm run app          # сборка интерфейса + запуск Electron
npm test             # unit-тесты обновления
npm run test:smoke   # после npm run build; нужен графический сеанс
npm run dev          # только веб-интерфейс, без нативного обновления
```

В Linux smoke-тест выполняется через `xvfb-run -a npm run test:smoke`; отключение Chromium sandbox в тесте применяется только для Linux CI. Производственная конфигурация окна использует `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`.

## 5. Ограничения и безопасность

- Сам Windows-установщик собран кросс-компиляцией в Linux. Запуск Electron-интерфейса и логика обновлений проверены, но установку/удаление на настоящей Windows и полный цикл 1.5.1 → 1.5.2 надо проверить отдельно. Подробности — `TEST-REPORT.md`.
- Исходный проект — интерфейс лаунчера с локальными профилями. Установка/запуск игр, серверная авторизация и синхронизация профиля **не добавлены**: по согласованному объёму исправлены запуск и самообновление лаунчера.
- Обновления загружаются по HTTPS; библиотека проверяет SHA-512 из `latest.yml`. **Это контроль целостности, не подпись издателя**: при захвате GitHub-аккаунта злоумышленник может подменить и EXE, и хэш. Включи 2FA, защити доступ к репозиторию. Для выпуска с подписью включи подписание в `electron-builder.cjs`, проверку подписи обновлений и настрой секреты CI.
- Не добавляй GitHub-токены, `.pfx`, `.env` и другие секреты в исходники.
- Шрифты могут загружаться с Google Fonts; без сети используются резервные шрифты. Основной интерфейс встроен в EXE.
- Крестик сворачивает в трей; для завершения нажми правой кнопкой на значок рядом с часами → **Выход**. Если трей создать невозможно, крестик завершает приложение.
- Если ранее использовалась старая Electron/Neutralino-сборка, устанавливай этот EXE вручную. Старый ZIP-апдейтер не умеет безопасно обновить весь рантайм. Совместимость прежних локальных профилей между разными оболочками не гарантируется.

## Что делать, если обновление не находится

1. Открой `/releases/latest` и убедись, что это опубликованный релиз, не draft/pre-release.
2. Проверь наличие EXE, `.blockmap` и `latest.yml` именно в **Assets релиза**, а не только в исходниках Git.
3. Новая версия должна быть строго больше установленной.
4. Проверь сеть и настройки автообновления. Ошибка сети теперь не выдаётся за «у тебя последняя версия».
5. Логи `electron-log` ищи в `%APPDATA%\temka-launcher\logs` или `%APPDATA%\TemkaLauncher\logs` в зависимости от имени приложения в установленной сборке.

### Если хочешь опубликовать уже приложенный EXE без пересборки

В архиве исходников есть папка `release-files/`: в ней лежат **соответствующие именно приложенному EXE** `latest.yml`, `.exe.blockmap` и SHA-256. Можно вручную создать на GitHub обычный публичный релиз `v1.5.1`, загрузить в Assets отдельный EXE и два файла метаданных из этой папки, затем опубликовать релиз. Не загружай туда ZIP с исходниками вместо установщика и не смешивай метаданные с EXE от другой сборки.

Это включит канал релизов, но не загрузит исправленные исходники в Git. Для последующих автоматических сборок всё равно нужно отправить проект. После ручной публикации 1.5.1 не пытайся повторно публиковать 1.5.1 через workflow: отправь исходники и запускай только сборку, а следующему релизу присвой 1.5.2.
