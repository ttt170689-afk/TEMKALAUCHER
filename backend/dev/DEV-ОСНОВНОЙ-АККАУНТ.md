# Dev из обычного лаунчера — основной аккаунт, только ПК

## Текущий результат

Исходники обычного ПК-лаунчера обновлены до **1.9.4**. В боковом меню появился **Dev**. Вход остаётся через рабочий основной Auth-проект: почта → код. Второй Dev-аккаунт для брата не требуется.

Уже установленный Dev-проект: `https://zykpirbzgiylkkasrllk.supabase.co`. Его старый owner остаётся административной точкой первого связывания. Ни обычный сервер друзей, ни его SQL/SMTP/пользователи не меняются.

**Новая миграция и Edge Function ещё НЕ установлены на живом сервере.** Без них вкладка честно покажет, что шлюз ещё не подключён. Исходники/локальная сборка не равны опубликованному EXE.

## 1. SQL только нового Dev-проекта

SQL Editor → New query → весь **Temka-Dev-Main-Account.sql** → Run.
Финальный результат: `TEMKA_DEV_MAIN_ACCOUNT_READY`.

Не запускать стартовую схему, прошлое назначение owner или обычный launcher backend повторно. Миграция добавляет отдельные main-UID таблицы, сохраняет файлы/старого владельца, закрывает прямые Dev Auth-загрузки и отключает старую систему активации приглашений из Dev-аккаунта. Для основного аккаунта будут создаваться НОВЫЕ приглашения.

## 2. Развернуть шлюз dev-gateway

В том же Dev-проекте: **Edge Functions → Deploy a new function → Via Editor**.
Название функции строго **dev-gateway**.

Удалить код примера и вставить **весь DEV-GATEWAY.ts** из комплекта. Это однофайловая версия; основной исходник с тестами хранится в `supabase/functions/dev-gateway/`.

Для этой функции отключить шлюзовую проверку **Verify JWT / Enforce JWT Verification / Verify JWT with legacy secret**. Название зависит от панели; настройка должна соответствовать `verify_jwt=false` в supabase/config.toml. Токен приходит из другого, основного Auth-проекта, поэтому автоматическая проверка JWT Dev-проекта отклонит его.

**Это НЕ отключает авторизацию приложения:** внутри функции обязательна серверная проверка токена через фиксированный основной `/auth/v1/user`. Если токен недействителен, чужого проекта, истёк, отсутствует или почта не подтверждена — запрос отклоняется до доступа к Dev-БД. Не удалять эту проверку и не заменять её чтением JWT payload/UID из тела запроса.

Нажать Deploy. Проверить, что URL заканчивается `/functions/v1/dev-gateway`.

Supabase автоматически предоставляет функции `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. Не копировать service_role/sb_secret в лаунчер, не отправлять их в переписку, не создавать публичную .env с ними. Сервисный ключ живёт только на сервере. Если в панели нет нужной настройки или функция выдаёт ошибку — прислать скриншот без секретов, не придумывать свои ключи.

### Вариант через CLI для умеющих

В корне этого серверного комплекта:

```bash
supabase login
supabase functions deploy dev-gateway --project-ref zykpirbzgiylkkasrllk --no-verify-jwt
```

Не обязателен: пользователь может использовать редактор панели.

## 3. Собрать обычное обновление с кнопкой Dev

**TemkaLauncher-1.9.4-sources.zip** — исходники одного ПК-проекта, подходит обычному ZIP-потоку TemkaPublisher.
Версия **1.9.4**, не перезаписывать выпущенные теги. Публикация этого ZIP добавляет вкладку в обычный лаунчер; сама по себе она НЕ публикует закрытые сборки в Dev.

Большой Windows-инсталлятор не создавался и не скачивался в рабочую область. Можно сначала сделать локальную сборку штатным способом; общий релиз публиковать только после проверки серверной связки.

## 4. Первый вход владельца

Открой лаунчер1.9.4, войди в свой ОСНОВНОЙ аккаунт и нажми **Dev**.
При первой успешной проверке подтверждённая почта основного аккаунта должна совпадать с подтверждённой почтой ранее назначенного Dev-owner. Шлюз проверяет основной аккаунт сервером, затем один раз связывает owner с его основным UID.

После этого права проверяются по основному UID, не по нику или почте. Другой пользователь с той же почтой не заменит уже привязанный UID; отключённый owner не включится обратно автоматически.

Если в двух проектах у тебя разные почты и вместо owner появляется форма приглашения, не выдавать себе tester-код и не удалять аккаунты. Нужна явная административная привязка подтверждённого основного UID; она ещё не выполнена и не делается угадыванием по имени.

## 5. Брат

Владелец: Dev → **Создать Dev-приглашение → Скопировать приглашение**. Передать брату лично.
Брат: обычный лаунчер1.9.4 → вход в СВОЙ основной подтверждённый аккаунт → Dev → вставить код → **Войти в Dev по приглашению**.

Один tester-слот, один код,24часа. Активированный доступ хранится сервером и восстанавливается при следующих входах, вводить код каждый раз не нужно. Код не принимается в игровом Beta Test. Dev-приглашение НЕ даёт права управлять игровыми бета-ключами — они по-прежнему только в Publisher.

Если место tester занято, владелец должен явно отозвать прежний доступ. Новый неиспользованный код отменяет старые неиспользованные. Пять отправок за10минут, шестая блокируется; проверка доступа не считается попыткой. Полный код хранится только в памяти UI после выдачи, сервер хранит hash, не plaintext.

## 6. Закрытый каталог файлов

Пока публикация Dev-файлов вручную через dashboard:
Storage → приватный `temka-dev` → загрузить файл.
Table Editor → `dev_builds` → product,version,точный object_path,SHA256,size_bytes,notes,published.

- `launcher-pc` — ПК-лаунчер, `fantazia`/`temkaworld` — игровые файлы.
- Сервер допускает только owner/tester; tester видит опубликованные, owner — также черновики.
- Каждый запрос файла заново проверяет основной токен и членство.
- Файл идёт через шлюз, клиент не получает подписанную Storage-ссылку.
- Клиент проверяет размер и SHA256 до передачи на сохранение. Файл не запускается автоматически.
- Снятая с публикации/отозванная сборка не выдаётся тестеру.

**Лимит этой реализации —50МиБ на файл.** Большой Windows EXE/игра потребуют закрытой разбивки/другого хранилища; это не реализовано. Не считать каталог уже готовым обновлятором больших инсталляторов.

## Что НЕ реализовано

- Нет отдельного раннего Dev EXE с другим appId/данными или автоматической установкой обновлений из Dev.
- Нет Dev-публикации в Publisher. Обычный Publisher публикует обычное обновление через GitHub, а не приватный Dev.
- Нет автоматического продвижения Dev-сборки в основной релиз.
- Нет переключения игровых/социальных backend на тестовую БД при запуске ранней сборки: пока сделан доступ и каталог, не полный отдельный игровой сервер.
- Нет игровых билдов, фактического запуска игры, Dev Android/iOS (телефоны отложены).

Скачанный файл можно передать дальше. Отзыв прекращает НОВЫЕ серверные запросы, но не отзывает уже полученные байты. Администратор с service_role имеет привилегированный доступ — его ключ хранить только на сервере.

## Проверки

Локально: TypeScript, frontend production build,179 unit checks,109 post-restore checks,9 browser UI checks с mock API;18 main-account SQL checks в PGlite;14 gateway request tests с mock fetch. Дополнительные тесты стартовой/предыдущей системы приглашений отдельно в комплекте.

НЕТ реального сквозного входа твоим токеном, live Edge deployment, live теста брата, Windows-device проверки, выдачи готового большого EXE или платёжного теста. После установки SQL/Edge это нужно проверить на двух основных аккаунтах. Токены и OTP не присылать.
