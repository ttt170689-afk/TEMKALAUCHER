# Свойства игры и бета-коды — подключение владельцем

## Что уже сделано

На ПК и телефоне: Библиотека → ⋯ на карточке игры → Свойства. Панель доступна всем локальным пользователям. В ней информация об игре и раздел «Бета-тест».

Это **серверная** система, без мастер-кода в клиенте. Приложение не может само проверить секрет или выдать право. В выданных сборках сервер не настроен: панель открывается, поле доступно, отправка отключена с объяснением. Подтверждённый реальный аккаунт/развёртывание ещё потребуются. Локальные проверки ниже не означают публикацию сервера.

## Подключить

1. Создай свой проект Supabase либо используй уже подключённый проект друзей. Если он новый — сначала выполни `backend/supabase.sql` один раз по инструкции друзей. Если друзья уже настроены, повторять исходный friends SQL не нужно.
2. Выполни `backend/beta-access.sql` в SQL Editor. Этот дополнительный скрипт можно повторять; он не удаляет существующие данные. Нужны Auth, таблицы player_profiles и creator_roles из шага 1.
3. Настрой подтверждение почты/SMTP и OTP по инструкции друзей. В production включи защиту регистрации (CAPTCHA, лимиты Auth); лимит в beta RPC действует на аккаунт, а не на IP и не заменяет защиту от массовой регистрации.
4. В сборку добавляются **только** `VITE_TEMKA_SUPABASE_URL` и `VITE_TEMKA_SUPABASE_ANON_KEY` — публичный publishable/anon key. Не вставляй service_role, sb_secret, пароль базы или SMTP в клиент/ZIP.
   - ПК: публичные GitHub Actions Variables `TEMKA_SUPABASE_URL` / `TEMKA_SUPABASE_ANON_KEY`, как для друзей, затем новый выпуск через Publisher.
   - Android/iOS: собственный `.env.local` с VITE-переменными, затем `npm run build`, `npx cap sync` и новая native-сборка. Готовый APK этого сообщения собран без твоего сервера — настройка проекта не изменит уже установленный APK.
5. В лаунчере → Профиль → онлайн-раздел подтверди свою почту. Найди **UUID своего подтверждённого пользователя** в Supabase Auth → Users. Не определяй администратора по локальному имени.
6. Только в SQL Editor владельца выдай этому UUID роль. Пример ниже намеренно НЕ готов к выполнению: сначала замени текст в угловых скобках своим проверенным UUID.

```sql
insert into public.creator_roles(user_id, role)
values ('<UUID ТВОЕГО ПОДТВЕРЖДЁННОГО AUTH-ПОЛЬЗОВАТЕЛЯ>'::uuid, 'creator_admin')
on conflict (user_id) do update set role = excluded.role;
```

7. В онлайн-разделе создай свой онлайн-юзернейм. Открой свойства игры заново. Вкладка **«Управление»** появится только после серверной проверки роли.

## Создать приглашения

В «Управление» выбери:
- **Моё одобрение каждой заявки** — безопасный режим по умолчанию. Правильно введённый код создаёт pending-заявку; игра не разблокируется до твоего решения.
- **Доступ сразу после проверки** — сервер выдаёт approved-доступ при правильном активном коде.

Число игроков: 1–1000. Срок действия кода: 1–720 часов. Код генерируется сервером с криптографической случайностью; открытый текст показывается автору при создании. Скопируй его сразу и передай выбранным игрокам лично. В таблице хранится SHA-256 нормализованного кода, не открытый секрет. Не включай логирование тел RPC-запросов с кодами.

Срок относится к **вводу кода**, а не к длительности уже одобренного доступа. Код закреплён за одной игрой. Дефисы, регистр и пробелы не мешают вводу. Не подходящий к этой игре, просроченный, отозванный и исчерпанный код дают одинаковый отказ.

## Одобрять и отзывать

Игрок подтверждает почту в онлайн-разделе профиля, затем вводит код в свойствах выбранной игры. Доступ привязан к auth-аккаунту и игре, не к локальному нику и не к конкретному телефону.

Автор → Свойства → Управление → Обновить: видны последние 200 заявок и коды. Проверяй онлайн-имя и UUID получателя; не полагайся только на имя. Можно одобрить, отклонить либо отозвать ранее выданный доступ. Действия записываются в beta_audit.

Игрок после решения нажимает **«Проверить статус»**. Push/realtime-уведомления не подключены. Отключение кода блокирует только новые заявки: уже выданное право отзывается отдельно у игрока.

Место в лимите кода расходуется при создании заявки, включая pending; отказ/отзыв не возвращает место. Это предотвращает переполнение мест и повторные обходы. Для пользователя и игры существует одна запись. Повторный ввод не расходует место повторно, а отклонённый/отозванный игрок не обходит решение новым автоматическим кодом: восстановить право может только автор.

## Важная граница защиты

Это реестр разрешений, **а не защищённая раздача готовой игры**. Одобрение не включает кнопку запуска, не добавляет исполняемый файл и не гарантирует наличие бета-сборки. Дальше нужно подключить приватные файлы игры и проверять approved на сервере при каждом запросе скачивания/входа. Нельзя поместить постоянную публичную ссылку на закрытую сборку в клиент и считать её защищённой этой панелью. Нужны короткоживущие ссылки/токены, серверная авторизация игры и отдельные сборки Windows/Linux/Android/iOS.

## Проверка и эксплуатация

- В beta-таблицах включён RLS, прямые клиентские SELECT/INSERT/UPDATE/DELETE запрещены.
- RPC проверяют auth.uid(), подтверждённую почту и creator_roles. SECURITY DEFINER использует пустой search_path и квалифицированные таблицы.
- 5 вводов кода / 10 минут на аккаунт, включая неудачные. Отказ возвращается как JSON, чтобы PostgreSQL не откатил счётчик попыток.
- Параллельные запросы сериализуются: лимит мест не превышается, повторная активация идемпотентна.
- Следи за резервными копиями, лимитами хостинга и логами без кодов/токенов. Доступ к SQL Editor и админ-аккаунту должен быть только у тебя.

`test-beta.py` — тесты только для ОДНОРАЗОВОЙ локальной PostgreSQL-базы. Он создаёт имитацию Auth для проверки SQL. **Никогда не запускай его против реального Supabase**; production-скрипт — только beta-access.sql.
